# JUSAGE — HUMANS INSIDE THE LIMIT

**Tokenbound / 세계관·제품 디자인 바이블 v0.1**  
**상태:** 제품 방향 확정 · 101개 서사 시드 작성 · 실제 16px 아트/코드 구현은 별도  
**기준 제품:** 기존 Rust/Win32 Jusage. 새 저장소 생성/원본 이전/운영 설치본 교체를 뜻하지 않음.

## 1. 작품의 주장

> 우리는 AI로 더 많은 것을 할 수 있게 되었다. 그런데 언제부터인가, 남은 토큰을 세며 살아가고 있다.

Jusage는 남은 AI 사용량을 알려주는 실용적인 Windows 트레이 앱인 동시에, 인간이 토큰의 한도 안에 갇혀 살아가는 모습을 보여주는 작은 픽셀 세계다. AI를 단순히 악당으로 설정하지 않는다. AI는 능력과 편리함을 주지만, 그 능력에 의존하게 된 인간은 점점 **'남은 토큰'을 삶의 기준으로 삼는다.**

**태그라인:** `JUSAGE — Humans Inside the Limit.`

### 지켜야 할 역설 세 가지

1. **100%는 자유가 아니라 자유의 착각이다.** 풍족하지만 숫자 `100`의 바깥으로 나가지 못한다.
2. **100→0은 감소하는 게이지가 아니라 감정의 하강이다.** 풍요→습관→의존→불안→조급→절박→속박.
3. **초기화는 해방이 아니라 반복이다.** 0의 쳇바퀴에서 풀려나 100의 도시로 돌아오지만, 여전히 숫자 안에서 산다.

## 2. 스토리·그래픽 문법

- **숫자 = 환경:** 획은 절벽·집·계단·공장·벽·다리이고, 숫자의 빈 공간은 인간의 방·감옥·통로이다. 퍼센트 숫자가 배경에 놓인 텍스트가 아니다.
- **인간 = 단 하나의 주인공:** 모든 잔여량에서 동일한 인간. 낮은 잔여량일수록 자세·동선이 짧고, 케이블·벽·문에 의존한다. 얼굴·성격을 사실적으로 묘사하기보다 실루엣·행동의 리듬으로 감정을 드러낸다.
- **AI 연결 = 양면성:** 초반에는 편리한 연결선과 빛, 후반에는 몸을 당기는 줄과 닫히는 문. 특정 AI 기업을 직접 악의 주체로 표현하지 않는다.
- **감정 = 시간:** 100 근처는 길게 멈추고 여유롭게 움직인다. 하락할수록 짧은 멈춤, 반복, 움찔함과 붙잡음을 늘린다. 다만 0%에서도 트레이 전체를 요란하게 깜박이지 않는다.
- **색 = 심리의 추적:** 풍요는 차가운 청록, 의존은 탈색된 청록, 불안은 황갈색, 절박은 주황/적색. 색상에만 의미를 맡기지 않는다.
- **숫자 우선:** 기존 실용 제품의 핵심은 트레이에서 퍼센트가 즉시 읽히는 것. 장면 때문에 `98`이 `88`처럼 보이거나 `100`이 `10`으로 보이면 시각 FAIL.

| 99~90 | 안락한 감금 | 여유, 익숙함 | 방·발코니·다리에서 생활 |
| 89~80 | 편리한 의존 | 만족, 습관 | AI 단말기와 자동 통로를 사용 |
| 79~70 | 자동화된 일상 | 안정, 무감각 | 정해진 길만 반복 이동 |
| 69~60 | 첫 불안 | 의심, 초조 | 벽과 케이블이 조금씩 가까워짐 |
| 59~50 | 숫자를 세는 시간 | 긴장, 손실감 | 시계·문·자원 카운터를 의식 |
| 49~40 | 부서지는 여유 | 불안, 압박 | 통로가 좁아지고 벽이 금감 |

101개 상태의 **개별 장면 시드**는 `SCENE_STORY_MAP_0_100.json`에 모두 기록했다. 이것은 **101개 고유 콘셉트**이지, 101개 애니메이션이 이미 구현됐다는 뜻이 아니다.

## 4. 작품의 앵커 장면

**100 / 황금 우리**: `100`은 화려한 도시다. 밝은 정원·기계·축제가 있지만 바깥 문은 열리지 않는다. 단순한 '완충=탈출' 화면 금지.

**99 / 쌍둥이 탑**: 두 `9`의 고리를 잇는 다리를 사람이 걸어간다. 인간은 이 세계가 영원히 이어질 것처럼 느낀다.

**98 / 두 개의 방**: **기존 E안 유지.** 9 안에서 쉬고, 일어나 줄기를 내려오고, 8로 이동해 다시 쉰다. 16프레임/250ms 휴식 맥박이 보고되었으며 ASUS 원본에서 실제 파일 확인 후 기준선 확정. 이미 만들어진 장면을 시각 시안으로 대체하지 않는다.

**50 / 중앙의 문턱**: `5`와 `0` 사이 문이 절반만 열려 있다. 인간이 잔량을 인지하기 시작하는 시점의 상징적 장면.

**1 / 마지막 손**: `1`은 절벽이고 인간은 남은 한 손으로 버틴다. 개별 숫자에 작은 인간을 단순히 붙여 놓지 않는다.

**0 / 영원한 쳇바퀴**: `0` 자체가 바퀴이자 감옥이다. 인간은 AI를 다시 쓰기 위해 계속 달리지만, 위치는 변하지 않는다.

**RESET / 거짓 해방**: `0→100` 변화 시 숫자 안의 문이 잠깐 열리는 듯하다가 다시 닫힌다. 큰 연출은 오프스크린 상세 아트에 남기더라도 트레이에서 숫자는 변함없이 읽혀야 한다.

## 5. 16px은 한계이자 미학

트레이는 제품의 주 화면이다. 팝업이 열리지 않아도 현재 잔여량과 분위기를 느낄 수 있어야 한다. 하지만 16×16 공간에 표정·사람·숫자·서사를 전부 사실적으로 묘사하는 것은 불가능하다고 가정하고 검증한다. **확대 콘셉트 아트가 실제 트레이에서 그대로 보인다고 주장하지 않는다.**

이를 위해 **두 단계의 동일한 디자인 언어**를 사용한다.

- **16px 실사용 심벌:** 퍼센트 먼저, 상징적 실루엣/공간, 명확한 대비, 짧은 동작, 적은 프레임. 사용자가 '숫자 안에 존재가 있다'는 것을 느끼는 수준이 현실적 1차 목표.
- **확대 장면:** 같은 픽셀 구조의 감정·인간 행동을 읽을 수 있게 보여줌. 필요 시 사용자가 팝업을 열거나 아이콘을 가리키면 장면 제목/짧은 문장을 확인하도록 하는 선택적 보조 기능. **의미를 전부 팝업으로 떠넘기지는 않는다.**

`100`은 세 자리라 가로 공간 문제가 더 심하다. `100` 가독성이 약해지는 순간 이야기는 정적 프레임 또는 툴팁에 남기고 숫자를 우선한다.

## 6. 개발 설계: 101개 상태 / 재사용 가능한 모션 문법

코드와 이미지의 수를 101×매프레임으로 무작정 늘리지 않는다. `SCENE_STORY_MAP_0_100.json`의 서사 데이터와 실제 그림 그리기/모션 엔진을 분리한다.

- `scene_for(remaining_pct)` : 0..100 가운데 정확한 번호를 선택. 실사용 데이터는 절대 수정하지 않는다.
- `scene_geometry` : 각 숫자의 획·고리·절벽·문 지형을 정의. 장면마다 고유 공간을 구성할 수 있게 한다.
- `actor_trajectory` : 같은 사람의 이동 경로·휴식 위치·움직임을 정의.
- `motion_language` : 걷기/매달림/조작/휴식/실패/반복을 작은 재사용 동작들로 만들되 장면별 리듬은 고유하게 한다.
- `render_native` → 실제 Windows 트레이 렌더링과 같은 경로를 통해 16px 유사 결과를 생성하고, MainPC에서 실기 검수한다.
- 상태가 변하면 `old_pct`와 `new_pct`를 구분해 장면을 전환한다. 퍼센트 하락과 초기화 상승을 다르게 표현하되 0→100에서 운영 API의 의미를 임의로 추론하지 않는다.

개발용 `--tray-playground --tray-value N`을 사용한다. 다중 상태 시뮬레이션도 실제 인증·사용량·기록과 철저히 분리한다. 실행 중 아이콘 핸들/리소스를 정리하고 Reduced Motion·정적 아이콘 설정을 유지한다. 성능 기준은 실측으로 정한다.

## 7. 첫 번째 제작 범위 — '감정의 전체 호' 세로 절편

**설계:** 모든 퍼센트의 세계관은 먼저 결정한다(이 문서 + JSON). **구현:** 100·98·50·1·0 + 97/99 연결성을 먼저 검증한다. 가장 풍요로운 장면, 중간의 불안, 마지막 매달림, 쳇바퀴, 기존 실증 E안을 포함하므로 콘셉트의 시작/중간/끝을 테스트할 수 있다.

1. ASUS 원본의 dirty/untracked/ignored, E안 소스와 실제 MainPC EXE를 대조한다. GitHub의 과거 링 구현으로 덮어쓰지 않는다.
2. 기존 98% E안의 16프레임 렌더를 기준으로 고정한다.
3. 100·50·1·0 의 정적 16px 심벌과 확대 장면을 설계한다. 97/99는 98과 자연스럽게 연결되도록 스케치한다.
4. 각 장면의 인물과 숫자 상호작용을 유도할 4~16프레임만 구현한다. 처음부터 101개 전체 렌더는 하지 않는다.
5. Windows 사용자 세션의 실제 트레이 녹화 및 CPU/메모리/GDI 수치를 확보한다. 인물 동작이 읽히지 않으면 숨기지 않고 수정한다.
6. 사용자 시각 검수 뒤 나머지 101개를 챕터별로 구현한다. 안정성 기준이 없는데 밤새 움직이는 애니메이션을 상시 실행하지 않는다.

## 8. 완료 기준과 보존

- **세계관 성공:** 100→0 하강을 정지 프레임과 최소한의 움직임만으로 알아볼 수 있다. 0·1·98이 별개의 장식이 아니라 하나의 인간의 서사임을 표현한다.
- **트레이 성공:** 16px 실제 배율에서 0/1/50/97/98/99/100 숫자가 즉시 읽히고, 실제 트레이 캡처가 보존된다.
- **기술 성공:** MainPC에서 PlayGround만 실행. 운영 Jusage PID/설정/기록/인증 불변, GDI/icon 핸들 정리, 깜빡임 없는 실행, 정지·Reduced Motion 검증. PASS 여부는 실측으로 판정.
- **배포 준비:** Git 변경을 식별하고 private/secret/ignored 아티팩트는 제외하여 별도 작업 브랜치와 Draft PR 형태를 마련. 사용자 동의 전 운영 설치본 교체·main 병합·공개 릴리스 없음.
